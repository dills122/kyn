# v0.1.3 usability and onboarding review

Reviewed 2026-09-05. Status: findings and proposed follow-up work; not a new
product specification or a published tutorial.

## Assessment

Kyn has the features needed for a useful first experience: presets, explicit
path inputs, resolution previews, clause explanations, and actionable expected
file paths. The largest opportunity is to teach those features through one
complete example before asking readers to design their own policy.

The current documentation works better as a reference for someone who already
understands the model than as a first lesson. A newcomer can reach `PASS`
without proving that any rule ran. They can also edit a file, run the default
command, and see no change because the default Git comparison uses commits.
These are the first improvements to make.

This is an expert walkthrough backed by CLI experiments, not a study with new
users. Friction and priorities below are reviewer judgments; no onboarding time
or conversion rate was measured.

## What to preserve

- The opening review problems are concrete: stories, tests, and module READMEs.
- Recipes already include directory layouts, complete policies, failure/pass
  commands, and links to executable fixtures.
- `--dry-run-resolve` gives exact paths; `explain` gives clause-level reasons,
  including skipped rules. These are strong teaching tools.
- The severity/threshold explanation and troubleshooting guide cover important
  distinctions accurately.
- The install page offers platform choices and separates contributor builds
  from released installs.
- The documentation site is readable and has a useful navigation structure.
  Improving the learning sequence is more valuable than changing its theme.

## U1 — Make the first result demonstrably useful

**Evidence:** [Getting started, steps 3–6](../site/getting-started.md#3-adapt-the-paths)
requires users to adjust globs and templates before showing a directory layout,
actual output, or an expected rule count. The README uses
`path/to/example.component.ts`, while the generated web preset matches `src/`.
The [home page](../site/index.md#start-in-five-minutes) goes directly from
`init` to automatic Git mode.

With an untouched `web-ui` preset, the literal README preview produced
`Matched instances: 0`. Its two-file check produced:

```text
PASS

Rules failed: 0
Warnings: 0
Infos: 0
```

The docs do tell readers to substitute real paths. This is not an assertion that
the placeholders are intended as real files. The usability problem is that a
failed adaptation looks successful, and the walkthrough does not explain how to
recognize that outcome. `--show-passes` alone does not make an empty evaluation
obvious.

**Improve:** Make `getting-started.md` a self-contained exercise with actual
source and kin files, one family, one rule, exact commands, and expected output.
Use explicit file input so the lesson does not depend on Git history. Preview
one matched instance, deliberately fail, explain the failure, then pass. Move
“adapt this to your repository” after that result. Link to this exercise from
the README and homepage instead of maintaining three different mini-tutorials.

**Acceptance:** Copying the exercise into an empty directory produces exactly
one matched instance, one failed rule with exit 1, then one passed rule with
exit 0. A nonmatching path and a skipped rule are explicitly distinguished from
a passed assertion. Kin files must actually be created in the setup.

## U2 — Explain which changes the default command sees

**Evidence:** [Getting started](../site/getting-started.md#5-run-the-policy)
states `origin/main...HEAD`, but does not translate that into staged/unstaged
behavior. [Git collection](../../internal/changes/git.go) runs a three-dot diff
between refs. In a disposable repository with `origin/main` at the initial
commit, changing a tracked component produced these results:

| State | `kyn check --verbose` | Same source supplied with `--files` |
| --- | --- | --- |
| Edit unstaged | `PASS`, `changed=0`, `instances=0` | Source can be evaluated explicitly |
| Edit staged | `PASS`, `changed=0`, `instances=0` | Failed existing-story rule, exit 1 |
| Edit committed | Failed existing-story rule, exit 1 | Same policy can be evaluated explicitly |

**Improve:** Put “Default Git mode checks committed changes since the merge
base; it does not include staged, unstaged, or untracked changes” next to the
first automatic-mode command. Define `origin/main`, `HEAD`, and the merge base
in ordinary language. Show separately how to supply a deliberate path list for
local policy trials. Explain that kin existence is checked in the current
checkout, so selecting refs does not check out their files.

The daily-work guide can add tested recipes for unstaged tracked files, staged
files, and untracked files. Label their scope and manual-input status behavior;
do not present one `git diff` command as covering all three. Keep status-aware
rules on Git input when added/renamed status matters.

**Owner:** `getting-started.md` for the first warning; `concepts.md` for input
semantics; `troubleshooting.md` for “I changed a file but nothing happened.”
Changing default CLI semantics is not necessary for this correction.

## U3 — Teach “already exists” versus “must exist”

**Evidence:** All four [starter generators](../../internal/cli/init.go) use
`if.kinExists`. With a matching component path but no story or spec on disk,
`check --show-passes --fail-on-empty` still exited 0. `explain` showed zero
passed rules and two skipped rules. The source matched, so `--fail-on-empty`
correctly did not fire.

The configuration reference and recipe adaptation notes explain the distinction,
but a newcomer reaches a reassuring `PASS` before encountering those details.

**Improve:** Introduce these two policies side by side, with the reason to
choose each:

| Policy | Placement | Kin absent | Kin exists but is not in the change set |
| --- | --- | --- | --- |
| Keep existing tests synchronized | `if.kinExists: [test]`, `assert.kinChanged: [test]` | Rule skipped | Rule fails |
| Require a test and its change | `assert.kinExists: [test]` and `assert.kinChanged: [test]`; omit `if.kinExists` | Rule fails | Rule fails |

The first supports gradual adoption without requiring every legacy source file
to acquire a companion immediately. The second enforces creation as well as
change membership. Both are useful; their guarantees differ.

**Acceptance:** The tutorial explains why the chosen rule skips or fails when
the test is absent, and explicitly says that `--fail-on-empty` detects zero
family instances, not zero applicable rules. Do not enable that flag globally
as a blanket fix: a README-only PR can legitimately match no source family.

## U4 — Make pass, skip, severity, and failure readable

**Evidence:** A passing generated story rule rendered this under `--show-passes`:

```text
[ERROR] story-sync
Family: web-component
Instance: src/button/button
Status: pass
Message: Source changed but story did not.
```

[Text rendering](../../internal/report/text.go) prints severity and the configured
message for every included result. This is consistent with the implementation,
but appears contradictory. Normal output also omits passed/skipped counts and
the active input mode. `explain` provides more context, but users have to know
when to invoke it.

**Improve now:** Annotate real output: `[ERROR]` is configured severity;
`Status` is this evaluation's outcome; `Message` is static policy text. Explain
that `explain` is diagnostic and can exit 0 when a rule fails. Explain warning
thresholds at the first warning example, not only in reference material.

**Separate product follow-up:** Consider status-first text labels, a clearly
labeled static policy message, and a concise no-evaluation notice with a next
command. Show the active Git range when useful. Preserve exit semantics and
machine contracts; any text-output changes require deliberate golden-fixture
review. Do not add a new command or schema solely to improve these labels.

## U5 — Reveal preset assumptions before asking users to choose

**Evidence:** [Presets](../site/presets.md) describes `web-ui` as components,
stories, and tests, but its source patterns are specifically
`src/**/*.component.ts` and `src/**/*.component.html`. Supplying
`src/Button.tsx` produced zero family instances and exit 0. This is an
Angular-style starter, not automatic frontend-framework detection.

The `api` preset assumes Go handlers/services under `internal/`; `iac` assumes
Terraform under `terraform/`. A proto preview mapped `proto/orders.proto` to
`gen/proto/orders.pb.go`, which is not the same as `gen/orders.pb.go`.

**Improve:** Expand the preset comparison with literal source/kin pairs,
existing-kin behavior, and blocking severity. Add one worked React or Vue
adaptation and explain what each changed glob/template does. For proto, show
the exact generated directory layout and why `{dir}` includes `proto/`.
Identify unsupported layouts explicitly without implying that new presets are
required for every framework.

**Acceptance:** A reader can choose a preset from their actual filenames and
preview the correct counterpart without opening the generator's Go source.

## U6 — Remove inactive concepts from the first lesson

**Evidence:** The [complete v2 example](../site/config.md#complete-v2-shape),
recipes, and generated starters contain additional `tests`, `story`, `stories`,
`docs`, or `generated` groups. The same reference accurately says other groups
are reserved and cannot currently be referenced by rules. Only `source`
creates instances; kin checks use the full change set.

**Improve:** Use only `groups.source` and `kin` in beginner examples. Keep
compatibility and reserved-field details in the reference. Explain direction:
a source change can trigger a related-file requirement; a story-only change
does not automatically trigger a reverse requirement. A story-only change in
the experiment produced no matching instance.

Commenting or simplifying generated starter YAML is a separate small change
with generator-test review. Avoid suggesting that reserved groups are a way to
implement reverse relationships today.

## U7 — Set expectations about the guarantee

**Evidence:** The opening promise is to keep related files aligned. The
[concepts page](../site/concepts.md) says Kyn does not inspect language syntax,
but the first-run examples do not explain what supplying `--files` means.
Supplying a source and story path satisfied change membership even without
editing their contents. An explicitly listed source need not exist on disk;
kin existence is a separate check.

**Improve:** Lead with a concrete explanation such as:

> Kyn catches a common review omission: changing a source file without including
> its related test, story, or documentation. You define the relationship once,
> then check each change locally or in CI. Kyn checks which paths changed and
> whether related files exist. Your tests and reviewers establish whether the
> accompanying changes are correct.

Label manual examples as simulated change sets. State that Kyn neither edits
the listed files nor runs tests. A green policy result does not establish test
quality or documentation accuracy. Explain when strict synchronization is
useful and when a warning or a narrower source pattern avoids needless edits.

**Owner:** A short statement on the homepage and README; fuller reasoning in
`concepts.md` and the policy-design guide. This is a product explanation, not
a reason to expand the MVP into content analysis.

## U8 — Provide a continuous route into everyday use

**Evidence:** “Getting started” is nested under Install. The next customization
step opens a reference that begins with the complete schema and compatibility
details. [CI adoption](../site/ci.md) offers useful provider examples, but the
first lesson has not established a verified policy or a reproducible failure.
Advanced report integrations arrive alongside initial rollout guidance.

**Improve:** Organize the learning route as:

1. **Start here:** what problem Kyn solves; choose an install method.
2. **Your first check:** a disposable, complete fail/explain/pass exercise.
3. **Use your own repository:** choose one convention, map real filenames,
   exclude generated areas, and deliberately verify both outcomes.
4. **Daily local use:** committed versus staged/unstaged/untracked scope,
   config location, and diagnosis of no matches or skipped rules.
5. **Adopt in CI:** commit the config, pin Kyn, make the intended base available,
   start with the chosen warning/error policy, and test a deliberately failing
   PR before relying on the check.
6. **Reference and advanced recipes:** all fields, formats, migration, and
   machine integrations remain easy to find without being prerequisites.

Each recipe should explain prerequisites, why the policy is useful, exact file
layout, field choices, expected failure, meaningful remedy, and limitations.
Add explicit handoffs between pages. The advanced SARIF example already notes
that `continue-on-error` needs a final gate when enforcement is desired; a
follow-up should make that gate copyable and show how setup failures are handled.

## Example of the proposed teaching style

The following is a content sketch for the new tutorial. The API path relationship
is already exercised by the repository's Go recipe fixture. A published version
must include the directory/file setup and a complete one-rule config before
these commands; this excerpt is not a replacement quick start.

> Imagine your team reviews Go handlers. When `order_handler.go` changes,
> reviewers usually ask whether `order_handler_test.go` needs an update. We will
> turn that convention into one check, then deliberately break it so you can see
> that it works. No Go compilation is needed for this exercise: Kyn works with
> paths, and these are disposable example files.

Start by showing both files, actually creating them in the exercise setup:

```text
internal/order/
├── order_handler.go
└── order_handler_test.go
```

Explain the mapping beside the policy rather than sending readers to a table:

| Config choice | What it means here | Why we chose it |
| --- | --- | --- |
| `include: ["internal/**/*_handler.go"]` | Handler files create instances | Ordinary test-only edits should not trigger this rule |
| `test: "{dir}/{name}_test.go"` | Keep the directory and `order_handler` name, append `_test.go` | This matches the existing Go test convention |
| `if.kinExists: [test]` | Apply only when the test exists on disk | Start by protecting existing coverage |
| `assert.kinChanged: [test]` | Require the test in this change set | Existence alone does not prove it was included |
| `severity: error` | A failed assertion blocks `check` by default | Make the deliberate failure visible in this lesson |

Then introduce the first command as an experiment:

> Tell Kyn that only the handler changed. `--files` supplies a simulated change
> set; it does not edit files or ask Git which files changed.

```bash
kyn check -c kyn.config.yaml --files internal/order/order_handler.go
```

> Expect exit 1 and `Expected files: internal/order/order_handler_test.go`.
> That failure is intentional. The handler matched our source pattern, its test
> exists, and the test was absent from the supplied change set. We now know the
> rule is active.

```bash
kyn explain -c kyn.config.yaml --files internal/order/order_handler.go
```

> Read `If` first: the source changed and the test exists. Read `Assert` next:
> the test was not included. `explain` returns exit 0 when it successfully
> explains this result; use `check` to enforce it.

```bash
kyn check -c kyn.config.yaml \
  --files internal/order/order_handler.go,internal/order/order_handler_test.go \
  --show-passes
```

> The assertion now passes because both paths are listed. In real work, make a
> meaningful test update where the policy requires it, then check the actual
> change set. This demonstration has proved the path relationship, not the
> quality of a test. Next, we will adapt the source pattern and test path to your
> own repository.

This sequence supplies the reason, the command, the expected observation, and
the interpretation at each step. Longer explanations belong where the reader
is making a decision, rather than in a larger field catalog at the start.

## Suggested delivery order and completion checks

| Increment | Scope | Completion evidence |
| --- | --- | --- |
| 1. Guided first run | U1–U3 and U7; tutorial plus README/home entry links | Fresh-directory exercise gives one known match, failure, explanation, and pass; covers skipped and unmatched outcomes |
| 2. Adaptation and adoption | U5, U6, U8; preset comparison, real-repository and daily-use guidance | Each documented layout resolves to expected kin; provider recipe uses the intended base and actually fails for the deliberate violation |
| 3. CLI presentation | U4; independently scoped text/help/starter improvements | Focused CLI/report tests and reviewed golden changes; deterministic ordering, machine schemas, and exit behavior preserved |

For published documentation changes, build with `mkdocs build --strict`, check
navigation and links in the rendered site, and execute new tutorial commands.
Extend the existing black-box fixtures when a new tutorial introduces behavior
not already covered; do not merely assert that prose strings exist.

After the first increment, observe several developers unfamiliar with Kyn:
can they explain what a green result guarantees, produce a deliberate failure,
adapt the mapping to one real source file, and select the correct change scope
without coaching? Record where they hesitate. Treat a five-minute first check
as a target to validate, not a claim supported by this review.

This review adds a local report and index entry only. Product behavior and the
published user guides are unchanged; the increments above remain proposed.
